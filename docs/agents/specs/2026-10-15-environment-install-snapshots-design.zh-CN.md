# 环境安装快照

状态：已实现。

相关：[可复用云端环境配置](2026-10-12-repository-environment-design.zh-CN.md)。快照复用沙箱检查点的格式、S3 存储、归档检查和 `docker load` 流程。常量集中在 `cloud_agent_shared/environment_snapshots.py`。

## 目标

| 场景 | 没有快照 | 有快照 |
| --- | --- | --- |
| 同一环境开第二个任务 | 安装脚本从头跑，最长 15 分钟，agent 等装完才开始 | 从快照建容器，只跑启动脚本（和可选的更新脚本），几秒后开始 |
| 点"测试环境"通过 | 结果用完即删 | 自动排一次预构建，之后的新任务直接用 |
| 锁文件变了 | 完整安装 | 不用旧快照，完整安装，并在后台重新预构建 |
| 对话被恢复到另一台机器 | 安装记录在原机器磁盘上，安装脚本会重跑，不能重复执行的脚本会失败 | 不重跑 |

快照存 S3，任何机器都能用。S3 没有配置（管理员没开自动快照）时整个功能关闭，行为与没有快照一样。

## 核心决定

1. 快照只在专用容器里产生（后台预构建）。从不截取用户的对话工作区，也不保存环境测试的容器。这样快照里没有会话和对话数据，不需要冻结运行中的 Kata 容器，也不拖慢用户的回合。
2. 快照是安装完成后容器相对基础镜像的改动，不含源码。保存前删掉仓库已跟踪的文件和 `.git`，只留依赖目录、缓存和生成的文件。格式与检查点相同。
3. 只给严格匹配的新任务用（见"匹配"）：同一 owner，同一环境，安装指纹相同。
4. 命中快照的新任务：从快照建容器，导入本任务源码，跑更新脚本（如有），跑启动脚本，agent 开始。
5. "安装已完成"的标记写在容器里，检查点恢复和快照启动都能认出，不会重跑安装。
6. 快照出任何问题都不阻塞任务，退回从基础镜像完整安装。

不采用的做法：从用户第一个任务的工作区截取（带着对话状态，要在运行中的 Kata 容器上停机，时机和回合纠缠）；只共享包下载缓存（仍要解压、编译，可作补充）；推到 OCI 镜像仓库（要多运行一个服务）；允许快照用旧基础镜像（新任务会跑在旧镜像上，CLI 和 helper 版本可能与当前 host 不兼容）。

## 快照怎么产生

### 时机

- 环境测试通过：为测试所用的提交排一次预构建。同一提交上这份安装已有可用快照时不排。
- 新任务没有可用快照而环境有安装脚本：自动排一次后台预构建。
- 用户点"重新预构建"。

同一匹配键同一时间只有一个在排队或进行（部分唯一索引）。同一份安装最近 6 小时内构建失败过，就不再自动排预构建，免得一个注定失败的脚本在每个任务旁边反复跑；测试通过和手动重建不受此限。

### 运行方式

预构建复用环境测试的运行记录和领取流程（`agent_environment_runs`），用 `purpose` 区分 `test` 和 `prebuild`。领取、租约、容量和孤儿清理都不变。

- 预构建：建临时组，导入源码，跑安装脚本，保存快照。只有预构建保存快照。
- 测试：安装、启动、验证，不保存快照，通过后排预构建。原因：启动和验证脚本能看到运行期 Secret，写出的文件可能带着它们。快照匹配只看安装指纹，运行期 Secret 轮换后旧快照仍会被选中，而新任务的脱敏和发布扫描认不出快照里那份旧值。也不能在安装和启动之间保存，因为保存前要删源码，之后无法继续启动和验证。代价是测试通过后要在另一个容器里再装一次。
- 取消：删除快照、删除环境或点"重新预构建"时，旧快照还在排队或进行的预构建一并取消。排队一天仍没有 host 开始的预构建由维护任务放弃：先标快照失败，再标运行失败。
- 回执：只有运行仍有效（未取消、租约未过期、未超过 30 分钟）时才接受。核对和把快照标为可用在同一个事务里并锁住运行记录。

保存快照由 runner 请 Sandbox Manager 完成，因为 S3 凭据只在 Sandbox Manager 里，且它只接受带环境测试标签的容器：

1. 计算锁文件指纹。
2. 写入"安装已完成"标记。
3. 以沙盒用户身份删掉已跟踪文件和 `.git`。
4. 停止容器，`docker commit`，导出新增层，上传 S3。
5. 本机保留 commit 出的镜像供之后的新任务使用。

### 存储

- 对象：`cloud-agent/sandbox/env/v1/<sha256(owner)>/<快照 id>.oci.tar`，在现有前缀下，不需要改 IAM。归档里的镜像名由 `SNAPSHOT_IMAGE_REPOSITORY` 加 `<sha256(owner) 前 16 位>:<快照 id>` 组成。
- 回执由 host 上报：对象位置、版本、SHA-256、大小、新增层大小、基础镜像、各步耗时。大小上限与检查点共用，超过则记失败并说明原因。

### 锁文件指纹

预构建时，host 对快照所用提交里已跟踪的锁文件逐个算 SHA-256，记在快照上。锁文件按文件名判断，与安装脚本建议功能（`environment_source.py`）共用一份列表：`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`uv.lock`、`poetry.lock`、`Cargo.lock`、`go.sum`，再加 `bun.lock`、`Pipfile.lock`、`requirements*.txt`、`Gemfile.lock`、`composer.lock`。子目录里的也算（monorepo 也能正确失效），数量有上限。

## 新任务怎么用快照

### 匹配

控制面领取任务时，若绑定有安装脚本，就找一份 `ready` 快照随领取结果下发。条件：

- 同一 owner 和环境。
- 安装指纹相同：控制面对安装脚本和安装期可见变量的名与值算 HMAC，不存明文，与环境版本号无关。只改启动脚本或快捷操作，旧快照仍可用；改安装脚本、安装期变量或全局变量，指纹就变。
- 基础镜像 digest 等于领取方 host 上报的沙箱镜像。
- 快照建好不超过 25 天。

runner 拿到快照后，只在新建组时使用，已有对话的后续回合和检查点恢复不用。它克隆源码后，对本任务的提交算锁文件指纹：一致就让 Sandbox Manager 从快照建组；不一致就从基础镜像完整安装，并告诉控制面"锁文件已变"，控制面按本任务的提交排预构建。没有可用快照时，runner 在导入源码后上报"没有快照"和提交，控制面同样排预构建。由 runner 上报是因为领取时任务的提交可能还没确定。

### Sandbox Manager 从快照建组

在"接管现有容器""新建""恢复"之外加第四条路，请求带 `environment_snapshot` 时从快照新建：

1. 本机已加载过这份快照：按镜像名直接用。
2. 没加载过：按检查点恢复的流程，按 digest 拉基础镜像，流式下载并核对大小和 SHA-256，检查归档结构（镜像名必须正好是约定的名字），再 `docker load`。
3. 建容器：启动配置、网络、资源上限、磁盘配额都按 `ChatSandboxSpec` 重新指定，加快照标签。镜像身份校验扩展为：基础镜像、标签写的检查点镜像，或标签写的快照镜像。
4. 导入本任务源码，同普通新组，但导入前"清空未完成的首轮"只清 `/agent-state`，不清 `/workspace`，否则依赖会被删掉。
5. 权限准备：首轮之前把工作区开放给共享组。这一步以沙盒用户（UID 10001）运行，只改它自己的文件。快照里的安装文件属于安装用户（UID 30000），保持安装时的权限，进不去的目录直接跳过。

第 1–3 步任何一步失败，都删除容器并改从基础镜像新建，任务继续。校验失败（SHA、结构、镜像名）把快照标 `failed` 不再下发，网络等临时错误不改快照状态。

### 准备与更新脚本

- 安装步骤显示"使用安装快照"（带构建时间），不执行安装脚本。
- 环境有可选的**更新脚本**，只在从快照启动时运行，在启动脚本之前。它用安装期变量，上限 900 秒，用于代码生成、数据库迁移等与源码相关的步骤。失败时与安装失败一样阻止 agent，可重试。
- 启动脚本照常运行。

## 失效、清理与配额

- 被取代：同一匹配键有更新的 `ready` 快照，旧的标 `superseded`。
- 删除：环境被删除或归档；环境有了新版本或安装期变量指纹变了，旧快照 24 小时后删除（留时间给正在建组的任务）；连续 7 天没被使用。发布配置、收到构建回执时和维护任务（每轮轮流检查 20 个 owner）都会检查指纹，所以指纹早就变了而环境没再发布的快照也会停用。
- 最长使用 25 天，超过就不再下发，下次用到时完整安装并自动重新预构建。
- 每个 owner 总量默认 20 GiB，按最久没用的顺序腾出空间。
- 删除由 host 执行，因为控制面不一定有桶凭证。host 每 10 分钟取一次待删对象，删掉对象版本后回报，最久没尝试的排前，所以被桶拒绝的对象不会挡住别的。本地镜像由每台 host 自己清：列出本机的快照镜像，问控制面哪些属于已退役（删除中、已删除、构建失败）的快照，删掉这些，控制面不认识的不动。
- 删对象需要 `cloud-agent/sandbox/env/*` 上的 `s3:DeleteObject` 和 `s3:DeleteObjectVersion`，这是唯一新增且可选的权限。没有时删除失败会记录并重试，靠桶上这个前缀的生命周期规则（对象创建 30 天后过期，晚于 25 天上限）兜底。规则写在 `docs/developer/operations.md`。

## "安装已完成"标记

- 标记文件在 Sandbox Manager 管理的 broker 目录里，目录 0700、属主 root，沙盒用户读写不了也伪造不了。
- 内容：安装指纹（控制面随绑定下发的 HMAC）、写入时的绑定 id、快照 id（如有）。
- 写入：安装脚本成功后由 Sandbox Manager 以 root 写；保存快照时带快照 id 再写一次。
- 读取：host 磁盘上没有该容器的安装记录时（新建、恢复、换机器之后）读一次，指纹一致就认为安装已完成。绑定 id 也相同，说明是检查点恢复的同一个工作区，不重跑安装也不跑更新脚本。绑定 id 不同，说明容器来自快照，显示"使用安装快照"，跑更新脚本，再把标记改成本任务的绑定 id，以后恢复时不重跑更新脚本。
- host 磁盘上的记录仍用来判断"这次启动之后启动脚本跑过没有"。

## 数据模型

- `agent_environment_runs` 新增 `purpose`（`test` / `prebuild`，默认 `test`）和 `snapshot_id`。"每个 owner 同时只有一个测试"的唯一索引只约束 `purpose='test'`。
- 新表 `agent_environment_snapshots`：

| 字段 | 说明 |
| --- | --- |
| `id`、`user_id`、`environment_id`、`revision` | 归属；版本号只用于显示 |
| `setup_fingerprint` | 安装指纹（HMAC），匹配用 |
| `base_image` | 带仓库域名和 digest 的基础镜像地址 |
| `source_sha`、`lockfiles` | 构建用的提交；锁文件路径到 SHA-256 的映射 |
| `object_key`、`object_version_id`、`sha256`、`size_bytes`、`new_layer_bytes` | 存储位置与校验 |
| `state` | `queued` / `building` / `ready` / `failed` / `superseded` / `deleting` / `deleted` |
| `run_id`、`host`、`durations_ms`、`detail` | 构建的运行、机器、耗时、脱敏的失败原因 |
| `created_at`、`ready_at`、`last_used_at`、`use_count` | 清理与界面显示 |

`environment_id` 和 `run_id` 不设外键：环境只归档不删除，运行记录也不删除。

- 环境版本的脚本文档新增 `update_script`，随版本历史和 diff 一起保存。
- 绑定新增 `setup_fingerprint`，绑定时计算并保存，随领取下发给 host。

## 界面

- Settings 环境列表：每个环境显示"已预构建 · 2 小时前""预构建中"或"预构建失败"，行菜单有"重新预构建"和"删除快照"。
- 编辑器脚本页有"更新脚本（可选）"，说明"每次从安装快照启动时运行，用于代码生成、迁移等"。测试页说明"测试通过后会为这份安装排一次预构建。锁文件不变时，新任务会直接从它开始。"
- 对话的环境面板：安装步骤显示"使用安装快照（2 小时前构建）"，后面依次是更新脚本、启动脚本。
- S3 未开启时，环境卡片说明"管理员未开启自动快照，每个新任务都会完整安装"。

## 安全

- 只给同一 owner 用，不跨 owner 共享。Fork 从源容器复制，与快照无关。团队环境的快照对团队活跃成员共用，使用记录写在共用快照上，计入排队那名成员的配额，只有团队 Owner 和管理员能删除或重建，信任前提见 [Team 设计](2026-10-15-team-shared-workspace-design.zh-CN.md)。
- 快照内容不可信，因为是仓库代码在安装期写出来的。只有通过 SHA-256、结构和镜像名检查后才交给 `docker load`，与检查点恢复相同。
- 快照里可能有安装期 Secret（如安装脚本写出的 `.npmrc`）。匹配要求安装期变量指纹相同，所以拿到快照的任务持有同一组值，没有新增暴露。轮换 Secret 后指纹变化，旧快照停用并删除。发布扫描照常覆盖这些已知值。
- 运行期 Secret 不进快照：快照只由预构建产生，预构建只跑安装脚本，看不到运行期变量。
- 存储凭证沿用每台机器已有的归档长期钥匙，和检查点一样，不扩大权限。
- 预构建没有推理 grant、MCP 或 Git 写凭据，与环境测试相同。

## 兼容与限制

- 能力 `environment-snapshot-v1`：没声明它的 host 不会领到 `prebuild`，领取任务也不会收到快照。不需要改沙箱镜像。
- 安装指纹需要 `AGENT_SOURCE_CONTROL_ENCRYPTION_KEY`。没有时绑定不记指纹，不建快照，任务照常创建。
- 没有挂载 containerd 内容存储时，导出走 `docker image save`。导出时只写镜像引用的 blob，`index.json` 直接指向镜像清单，否则传统 overlay2 上多带的元数据 blob 会让加载端的检查拒绝它（检查点恢复同理）。
- 新对话在安装之前把 `/workspace` 存一份初始归档到 S3，从快照建的组依赖已在其中，初始归档会变大，与停止时的最终归档相当，现有大小上限够用。
- 新基础镜像发布后快照随之失效。staging 每天部署多次，影响大；生产影响小。
- 第一个任务仍是完整安装，同时后台多跑一次预构建，占一个容器名额。
- 机器第一次用某份快照要从 S3 下载，之后用本地镜像。
- 锁文件没变而依赖源码内容的安装步骤（如生成代码）需要用户写进更新脚本。
- S3 费用靠清理和总量上限控制。
